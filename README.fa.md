# Sanbuk API Spec

قرارداد عمومی API ترکینگ سنبوک — هر دو نیمه‌اش، تبلیغ‌دهنده و ناشر — و مرجعی که همه‌ی SDKهای رسمی در برابر آن بررسی می‌شوند.

**[English guide →](README.md)**

| | |
|---|---|
| [`spec/openapi.yaml`](spec/openapi.yaml) | توصیف OpenAPI 3.1 هر دو اندپوینت عمومی |
| [`postman/sanbuk-tracking.postman_collection.json`](postman/sanbuk-tracking.postman_collection.json) | هفت ریکوئست، به همان ترتیبی که باید امتحان کنید |
| [`postman/sanbuk-production.postman_environment.json`](postman/sanbuk-production.postman_environment.json) | محیط تنظیم‌شده روی edge پروداکشن |

پوشه‌ی `spec/` و فایل کالکشن از بک‌اند سنبوک تولید می‌شوند و با هر تغییر قرارداد خودکار sync می‌شوند. تغییری که اینجا بدهید با sync بعدی پاک می‌شود — به‌جایش issue باز کنید.

## تبلیغ‌دهنده: دو اندپوینت، و یک قاعده

```
POST https://t.sanbuk.com/v1/postback   # سرور به سرور — قابل صورتحساب
POST https://t.sanbuk.com/v1/pixel      # مرورگر — فقط راستی‌آزمایی
```

**پست‌بک منبع حقیقت مالی است.** فقط پست‌بک می‌تواند تبدیل قابل پرداخت بسازد.

**پیکسل برای راستی‌آزمایی و تشخیص تقلب است.** به‌تنهایی هرگز صورتحساب نمی‌سازد.

روی هر دو، `event_id` *یکسان* بفرستید. سنبوک آن‌ها را در پنجره‌ی ۴۸ ساعته جفت می‌کند، و همین جفت‌شدن تنها چیزی است که یکپارچه‌سازی از شما می‌خواهد درست انجام دهید.

## چک‌لیست یکپارچه‌سازی

۱. **`snbk_cid` را نگه دارید.** سنبوک آن را به آدرس صفحه‌ی فرودتان اضافه می‌کند. کنار سفارش یا کاربری که به آن تعلق دارد ذخیره‌اش کنید. بدون آن تبدیل ثبت می‌شود ولی به هیچ ناشری نسبت داده نمی‌شود و پولی بابتش پرداخت نمی‌شود.

۲. **`event_id` را چیزی بگذارید که از قبل مال شماست و هرگز تکرار نمی‌شود.** شماره‌ی سفارش ایده‌آل است. تکرار، پاسخ `200` می‌گیرد و چیزی را تغییر نمی‌دهد، پس تلاش مجدد همیشه امن است.

۳. **با `X-Sanbuk-Mode: test` تمرین کنید** تا وقتی اکشن در پنل «تأییدشده» بخورد. رویداد آزمایشی راه‌اندازی شما را تأیید می‌کند ولی از کیف پول خرج نمی‌کند، و رویدادی جدا از همزاد زنده‌اش است — پس تمرین با یک شماره‌ی سفارش واقعی آن را نمی‌سوزاند.

۴. **هدر را بردارید تا زنده شوید.**

همه‌ی مبالغ، عدد صحیح و به **ریال** هستند.

## ناشر: چهار فراخوان، و چهار تعهد

ناشر معمولاً یک SDK آماده نصب می‌کند — [`@sanbuk/js`](https://github.com/sanbuk-dev/sanbuk-js) برای وب، [`sanbuk-android`](https://github.com/sanbuk-dev/sanbuk-android) برای اپ، یا یکی از پوسته‌هایی که رویش ساخته شده‌اند. این نیمه از اسپک برای بقیه است: یک موتور بازی، یک فریم‌ورک، یا پلتفرمی که ما برایش پوسته‌ای منتشر نکرده‌ایم.

```
GET  https://t.sanbuk.com/ad?placement=…   # اینجا چه چیزی بکشم؟
GET  https://t.sanbuk.com/i/{code}?eid=…   # دیده شد
GET  https://t.sanbuk.com/c/{code}         # کلیک شد
POST https://api.sanbuk.com/api/v1/sdk/ping  # این رسانهٔ اپ واقعی است
```

پاسخ سروینگ تبلیغ را **توصیف** می‌کند — تیتر، متن، تصویر، متن دکمه، رنگ برند. هرگز نشانه‌گذاری نیست. هرطور که به اپ شما می‌آید بکشیدش؛ اینجا هیچ‌چیز برای شما رندر نمی‌شود، و همین نکتهٔ اصلی است.

هر کاری که SDKهای منتشرشده فراتر از این چهار فراخوان انجام می‌دهند، به چهار تعهد خلاصه می‌شود. نادیده‌گرفتنشان برای کسی هزینه دارد:

۱. **نمایش را فقط وقتی بشمارید که دیده شده** — دست‌کم نیمی از تبلیغ، یک ثانیهٔ پیوسته روی صفحه. شمردن در لحظهٔ رندر یعنی شمردن تبلیغی که کسی تا آن پایین اسکرول نکرده.
۲. **با هر ایمپرشن یک `eid` بفرستید و در تلاش دوباره همان را بفرستید.** شمارنده هویت رویدادی از خودش ندارد، پس گزارش دوبارهٔ بدون آن یک نمایش دوم است — و کمیسیون per-impression روی همین عدد پرداخت می‌شود.
۳. **کلیک را در مرورگر واقعی باز کنید**، هرگز در WebView داخل اپ. WebView سبد کوکی خودش را دارد، شناسهٔ کلیک first-party از آن جان سالم به در نمی‌برد، و کانورژن هرگز نسبت داده نمی‌شود: ناشر کار کرده و پولی نمی‌گیرد.
۴. **تبلیغ را برچسب بزنید.** خواننده باید بتواند آن را از محتوای خودتان تشخیص بدهد.

رسانه‌هایی که مستقیم ادغام می‌شوند برچسب می‌خورند و کمی دقیق‌تر پایش می‌شوند، به این دلیل ساده که ما دو تعهد اول را از اینجا نمی‌توانیم راستی‌آزمایی کنیم.

اگر پاسخ روزی با `"kill": true` برگشت، تا به‌روزرسانی ادغام‌تان دیگر درخواست نفرستید. یعنی نسخه‌ای که در `sdk` خودش را معرفی می‌کند دیگر پاسخ نمی‌گیرد، و این تنها راه ماست برای بازنشسته‌کردن کدی که همین حالا روی گوشی مردم است.

## امتحان کردن

کالکشن و محیط پروداکشن را در Postman ایمپورت کنید، `apiKey` و `pixelId` را از پنل تبلیغ‌دهنده پر کنید، و ریکوئست‌ها را از بالا به پایین اجرا کنید. ترتیبشان عمدی است: اول سندباکس، بعد زنده، بعد یک تکراری عمدی، بعد دو حالت خطا.

```bash
curl -X POST https://t.sanbuk.com/v1/postback \
  -H "Authorization: Bearer $SANBUK_API_KEY" \
  -H "Content-Type: application/json" \
  -H "X-Sanbuk-Mode: test" \
  -d '{
        "action": "purchase",
        "event_id": "ORD-10293",
        "click_id": "018f3c2e-7b1a-7c3d-9e4f-1a2b3c4d5e6f",
        "value": 25000000
      }'
```

پاسخ `202` یعنی رویداد تازه است. پاسخ `200` یعنی قبلاً دیده شده و چیزی تغییر نکرد. هر دو موفقیت‌اند.

## خطاها

روی `code` شرط بگذارید، هرگز روی `message` — پیام بومی‌سازی می‌شود و ممکن است تغییر کند.

| کد | HTTP | معنی |
|---|---|---|
| `invalid_api_key` | ۴۰۱ | کلید Bearer غایب یا اشتباه است |
| `invalid_pixel_id` | ۴۰۴ | هیچ ورک‌اسپیسی مالک آن شناسه‌ی پیکسل نیست |
| `unknown_action` | ۴۰۴ | آن کد اکشن در ورک‌اسپیس شما تعریف نشده |
| `value_required` | ۴۲۲ | این اکشن بر مبنای مبلغ قیمت‌گذاری می‌شود، پس `value` اجباری است |
| `validation_failed` | ۴۲۲ | بدنه نامعتبر است؛ `errors` فیلدهای مشکل‌دار را نام می‌برد |

پاسخ `429` یعنی محدودیت نرخ. صبر کنید و همان `event_id` را دوباره بفرستید — idempotency دقیقاً برای همین است.

## SDKهای رسمی

لازم نیست مستقیم با API حرف بزنید.

| زبان | پکیج | ریپو |
|---|---|---|
| JavaScript / TypeScript | `@sanbuk/js` | [sanbuk-js](https://github.com/sanbuk-dev/sanbuk-js) |
| PHP | `sanbuk/sanbuk-php` | [sanbuk-php](https://github.com/sanbuk-dev/sanbuk-php) |
| Python | `sanbuk` | [sanbuk-python](https://github.com/sanbuk-dev/sanbuk-python) |

هرکدام idempotency و تلاش مجدد با backoff و مدیریت click id را برایتان انجام می‌دهند.

## نسخه‌بندی

مقدار `info.version` در spec، قرارداد را دنبال می‌کند نه SDKها را. تغییرات شکننده پیشوند مسیر جدید می‌گیرند؛ بقیه‌ی تغییرات افزایشی‌اند.
